# Zomato Customer and Order Analytics

A MySQL 8 case study covering revenue, customers, restaurant performance, discounts, cancellations and refunds, and churn. The source workbook contains 50,000 orders, 4,999 customers, and 200 restaurants. Orders span January 2024 through April 2026.

| Folder | Contents |
|---|---|
| `data/` | Three UTF-8 CSVs exported from the supplied workbook |
| `sql/` | Schema, import, data validation, and 27 business queries |
| `results/` | One CSV per question, with prefixes matching query labels |
| [`report/findings.md`](report/findings.md) | Findings, recommended actions, and limitations |

## Run on MySQL 8

From the extracted project folder, connect to MySQL using the command below. Substitute your MySQL user if needed.

```sh
mysql --local-infile=1 -u root -p
```

At the MySQL prompt, run these in order.

```sql
SOURCE sql/01_create_schema.sql
SOURCE sql/02_load_data.sql
SOURCE sql/03_validate_data.sql
SOURCE sql/04_business_analysis.sql
```

Use an empty project schema for the first import. The user needs permission to create the database, tables, and views. The import also requires the server's `local_infile` setting to be enabled. If local file loading is unavailable, import the three CSVs into the existing tables using MySQL Workbench's Table Data Import Wizard in this order: customers, restaurants, orders. Review any import warnings and verify the counts in script 03. After loading once, rerun scripts 03 and 04 to refresh the checks and analysis.

The included results were generated by running the query logic on the supplied data through SQLite with MySQL syntax adapted where needed. The MySQL-specific schema and import were not exercised against a live MySQL server.

## Data model and preparation

Each order has one `order_id` and references a restaurant by `restaurant_id`. An order also carries a `customer_id`. Ten orders reference a customer ID absent from the customer file. Keep these orders for platform-wide and restaurant metrics. Customer-level metrics use matched customers.

The export trims the customer ID header, drops an empty customer column, and standardizes the one customer city value ` pune` to `Pune`. All data rows are retained. Customer results identify people by ID. The input customer CSV retains the provided names, so check permission or remove the names before uploading the data publicly.

## Metric definitions

| Metric | Rule |
|---|---|
| Delivered revenue proxy | Order amount minus discount plus delivery fee, for delivered orders. This is delivered customer order value. Platform commission and settlement data are unavailable. |
| Average order value | Average net order value among delivered orders |
| City | Restaurant city for revenue and discount volume. Customer city for churn. |
| Acquisition channel value | Average historical delivered order value per matched purchasing customer |
| Repeat customers | Matched customers with at least two delivered orders |
| Restaurant and cuisine volume | Count all recorded orders. Bottom five restaurants are ranked by delivered order value. High rating means at least 4.0. |
| Discount usage | Positive discount is the proxy. Discount penetration includes all orders. Customer spend groups are based on whether a matched customer has ever had a discounted delivery. |
| 90-day repeat rate | Whether a customer bought again on days 1–90 after their first observed delivered order. Include only matched customers with the full 90 days of follow-up. For tied first dates, use the lowest order ID. |
| Cancellation and refund rates | Orders with the corresponding status divided by all recorded orders |
| Cancelled order value | Net order value attached to cancelled orders, an estimate of foregone order value |
| Churn | A matched customer with a delivered order and at least 90 days since their last delivery, measured at the latest observed order date |
| High-value churn | Churned customers among the top spending quintile of matched purchasing customers |
| Churn revenue exposure | Historical delivered value of churned customers over the observed dataset. Future lost revenue cannot be estimated directly from the supplied files. |

The workbook contains 20,428 matched orders with dates before the recorded signup date. Repeat and churn measures rely on observed order dates. Acquisition comparisons describe historical spend by assigned channel and should be interpreted in light of the signup discrepancy.
